D0  Purpose and callers.
    Creates the TypeScript service's Postgres schema from numbered SQL files, and imports today's Python database into it once (FROM-SPEC spec.md:134, 773 "row counts match on a copy").
    Callers: `ctc migrate` (apps/cli) by the operator; every app at start calls `assertSchemaVersion` (T1.3+, T2+); T1.3 repositories read the tables built here; the T1.3 `tenancy` test walks every repository function; T7.1 runs `ctc migrate --from-python` against Supabase after the owner approves (FROM-OWNER O7). Today's producer of the data: the Python schema `src/ctc/storage/schema.sql` (read it for column names and types; do not copy its table layout, the target differs).
    The target is Postgres 17 + pgvector, schema `ctc` (FROM-SPEC spec.md:119).

D1  Trust.
    Connection URLs carry passwords: never printed, logged or put in an error or report (report shows schema and database name only). Migration files are ours (reviewed code) but their checksums are verified, so an edited, already-applied file is caught. The Python database is read-only input: opened in a read-only transaction, never altered, even by mistake (FROM-OWNER O3/O7 spirit; YOUR-CHOICE for the read-only guarantee). Source rows are data, not code: they are inserted only through parameters, never concatenated into SQL. Schema names are validated (D2) because they are the only identifier that goes into SQL text.

D2  Limits (module constants).
    Migration file name `^[0-9]{4}_[a-z0-9_]+\.sql$`; versions start at 1 and are contiguous (YOUR-CHOICE).
    Schema name `^[a-z_][a-z0-9_]{0,62}$` (FROM-CALLERS src/ctc/storage/store.py:71; the length cap is Postgres' identifier limit).
    Advisory lock key `7426001`, taken with `pg_advisory_xact_lock` inside each migration transaction: the same key the Python schema script uses, so extension creation by either stack is serialized (FROM-CALLERS src/ctc/storage/schema.sql:6).
    Import batch: 200 rows per INSERT; connection timeout 5,000 ms; no statement timeout set by us (YOUR-CHOICE; Supabase's pooler has its own).
    Default archive dir `~/.claudethecaller/archive`, default schemas `ctc` for the target and for the source (D3).

D3  Output and error format.
    D3a Public names in `packages/shared/src/repositories/admin/index.ts`, imported as `@ctc/shared/repositories/admin` (the `./*` export of T1.1 D3b matches this path):
        `loadMigrations(dir?: string): Migration[]`  where `Migration = {version: number; name: string; file: string; sql: string; checksum: string}`, `checksum` = sha256 hex of the raw file bytes. Default dir `packages/shared/migrations`.
        `migrate(o: {url: string; schema?: string; dir?: string; dryRun?: boolean}): Promise<{schema: string; before: number; after: number; applied: {version: number; name: string}[]; pending: {version: number; name: string}[]}>`  (`pending` = what a dry run would apply; empty otherwise).
        `schemaVersion(o: {url: string; schema?: string}): Promise<number>`  (0 when the schema or the stamp table is missing).
        `assertSchemaVersion(o: {url: string; schema?: string; dir?: string}): Promise<void>`  throws `MigrationError` code `schema_too_new` or `schema_behind`.
        `importFromPython(o: {targetUrl: string; targetSchema?: string; sourceUrl: string; sourceSchema?: string; dryRun?: boolean; archiveDir?: string}): Promise<ImportReport>`.
        `class MigrationError extends Error {code: ErrorCode}`; `ErrorCode` = `bad_name | gap | duplicate | checksum_mismatch | schema_too_new | schema_behind | bad_schema_name | sql_failed | same_schema | bad_source | unmapped_value | import_failed`.
        Message format: `<code>: <detail>`, e.g. `checksum_mismatch: 0003_graph.sql (applied sha256 ab12…, file sha256 cd34…)`. Details name files, versions, tables and counts; never a URL or a password.
    D3b `ImportReport = {source: {database: string; schema: string}; target: {database: string; schema: string}; dryRun: boolean; tables: TableReport[]; warnings: string[]}` with `TableReport = {table: string; from: string; source_rows: number; imported: number; skipped: number; skipped_by_reason: Record<string, number>; target_rows: number}`. `table` is the target table, `from` the Python table; one entry per mapping in D13, in the order of D13. `target_rows` = `count(*)` read back from the target after the writes (inside the same transaction). Reason codes: `exists`, `duplicate_hash`, `orphan`, `by_design`.
    D3c CLI (`apps/cli/src/main.ts`, run as `node apps/cli/src/main.ts migrate …`; `bin` name `ctc`; arguments parsed with `node:util` `parseArgs`, no CLI framework: YOUR-CHOICE):
        `ctc migrate [--schema S] [--dir DIR] [--dry-run]` applies pending migrations. Target URL = `loadConfig().database_url` (env `CTC_DATABASE_URL`); unset → exit 1, `CTC_DATABASE_URL is not set`.
        `ctc migrate --status [--schema S] [--dir DIR]` prints `schema <S>: version <n> of <latest> (up to date | behind | ahead)`, no writes; exit 0 only when up to date, else 1.
        `ctc migrate --from-python --source-url U [--source-schema S] [--schema S] [--dry-run] [--json] [--archive-dir D]`; `U` default env `CTC_PYTHON_DATABASE_URL`. Prints a table (default) or the `ImportReport` JSON on stdout (`--json`).
        Exit codes: 0 ok, 1 any `MigrationError` or other failure (stderr `ctc migrate: <code>: <detail>`), 2 usage (unknown flag, `--from-python` without a source URL, `--status` with `--from-python`) (FROM-SPEC spec.md:112; `--dir` is for tests, YOUR-CHOICE).
        A normal apply prints one line per applied file `applied 0003_graph.sql` and a last line `schema <S>: version <n>`; nothing to do prints `schema <S>: version <n> (up to date)`.

D4  Bad input.
    Migration files: a `.sql` file with a bad name → `bad_name`; two files with one version → `duplicate`; a hole in the numbers → `gap`; all found problems are listed in one error (YOUR-CHOICE). Non-`.sql` files in the folder are ignored.
    Database ahead of the files (stamp > latest file, or an applied version with no file) → `schema_too_new`; stamp behind the files in `assertSchemaVersion` → `schema_behind`, message ends `run: ctc migrate` (YOUR-CHOICE: refuse in both directions; FROM-SPEC spec.md:134 only requires the older-binary case).
    An applied file whose checksum differs from the stamp row → `checksum_mismatch`, nothing is applied (never "fix" history).
    A failing statement → `sql_failed: <file>: <Postgres message>`; that file's transaction is rolled back, earlier files stay applied.
    Import pre-flight (all before the first write, all problems listed together): source schema missing or lacking the Python tables `projects`, `memories`, `capabilities` → `bad_source`; target not at the latest version → `schema_behind`; same database and same schema → `same_schema`; a source value with no mapping in D13 (an unknown `origin`, `kind`, `action`, status…) → `unmapped_value` naming table, column and value counts. Nothing is written when pre-flight fails.

D5  Odd but harmless input.
    Running `migrate` twice, or on a fully migrated database, does nothing and exits 0. `migrate --dry-run` on a missing schema reports everything as pending and creates nothing, not even the schema. An empty Python database (all tables empty) imports as all zeros. A source table with 0 rows is fine. Python capability rows with no body import as an empty file. Importing twice is a no-op (D14). The Python tables `decisions`, `events`, `jobs`, `graph_sources` exist but are not imported (D13).

D6  Must never.
    Print or log a URL or password; write to the source database; leave a half-imported target (import is one transaction); apply a migration without the advisory lock; apply or import into a database other than the one named by the URL; touch any scratch database or role not named `ctc_t12_*` in tests (read-only use of the source copy `ctc` is allowed); delete data in the target (no `drop`, `truncate` or unqualified `delete` in migrations or the importer; migrations only create); hang (connection timeout D2, the CLI exits on error); rewrite an applied migration's stamp; run a migration whose file name or order was not validated.
    Does any of this break the structure callers rely on? T1.3's `tenancy` test needs every tenant table to carry `user_id` (D10), so the admin functions here live in `repositories/admin/` and take no `ctx`; T1.3 must skip that folder (listed in OPEN).

D7  Non-goals.
    No down migrations (forward only). No repositories, queries or Kysely types (T1.3). No queue tables beyond `jobs` (T1.4). No archiving of `decisions` and `events` (T0.3 writes `~/.claudethecaller/archive/*.jsonl.gz`; the importer only warns if they are missing, D14). No drop or rename of Python's schema (T7.1). No Supabase access (FROM-OWNER O7: scratch DB only; tests use `ctc-dev-pg`). No change to Python code. No vector re-embedding (vectors are copied as they are). No new config keys (T1.1 owns config). No file-to-version scanning (T3.1).

D8  Silence rule.
    Where this list says nothing, choose the more tolerant, less destructive behaviour and comment `judgment:`. Examples: unknown extra source columns are ignored; a source row that cannot be imported is skipped and counted with a reason rather than aborting, except enum values (D4 pre-flight) because skipping those silently would hide a vocabulary problem.

D12 Migration runner semantics.
    Files in `packages/shared/migrations/`: `0001_base.sql` (extensions, projects, sessions, history_files, jobs, idempotency_keys, api_keys, dedup_review), `0002_graph.sql`, `0003_library.sql`, `0004_memory.sql`, `0005_runner.sql` (YOUR-CHOICE: one file per feature so later tasks add `0006_…` rather than editing these). SQL is written with `{schema}` where Python's schema.sql writes it, replaced by the validated schema name before running; objects are always schema-qualified.
    Order: ascending version. Each file runs in its own transaction: `begin; select pg_advisory_xact_lock(7426001); <file>; insert into {schema}.schema_migrations …; commit`. Applied files are skipped by version; their checksum is compared first (D4). The stamp = `max(version)`.
    The runner creates the schema and `schema_migrations` itself (`create … if not exists`) before the first file, unless dry-run. Two runners at once serialize on the lock; the second finds nothing to do and exits 0.
    Migrations create objects only: `create … if not exists` is not required (versions guard re-runs) but nothing may drop or alter existing data.

D14 Import semantics (YOUR-CHOICE: the spec says only "one-time import"; atomic, idempotent, dry-run and read-only source are chosen for safety).
    One transaction on the target: everything is written or nothing is. The source connection is `read only` for its whole life. `--dry-run` runs the same code, reads the counts back, then rolls back; the target is unchanged (including sequences).
    Idempotent: every insert is `on conflict do nothing`; a second run imports 0 rows and reports each existing row as skipped, reason `exists`. Numbers must add up: for each entry `imported + skipped == source_rows`, and `target_rows` is the real count in the target. For a target that was empty, `target_rows == imported` for a 1:1 mapping.
    Sequences of identity columns (`wf_runs`, `wf_steps`, `api_keys`, `dedup_review`) are set to `max(id)` after the import so new rows do not collide.
    The importer needs the target at the latest version and refuses otherwise (D4).

D16 Tests and scratch databases (FROM-OWNER O7, O8).
    DB tests read `CTC_TEST_ADMIN_URL` (an admin URL of the scratch server, e.g. `postgresql://postgres:ctcdev@127.0.0.1:18304/postgres`). Each test creates a database named `ctc_t12_<random>` (and, where a test needs one, a login role named `ctc_t12_<random>`) and drops it afterwards; no other database or role is touched. With the variable unset the DB tests are skipped and say so; `selfcheck.py` fails if any test was skipped. The Python-schema source is built in a temp database by running `src/ctc/storage/schema.sql` with `{schema}` → `ctc` and inserting the test's own rows. An optional second source is a real copy: env `CTC_TEST_PY_COPY_URL` (+ `CTC_TEST_PY_COPY_SCHEMA`, default `ctc`) names a restored `pg_dump` of the Python database; it is only read. Tests assert counts from SQL run against the databases themselves, not from the importer's own report alone.
