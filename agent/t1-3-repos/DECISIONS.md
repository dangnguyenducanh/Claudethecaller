Tag rule: a tag at the end of a block of indented lines covers the whole block above it (D6, D10, D12-D14 of T1.3; D15, D16, D18 of T1.4).

D0  Purpose and callers. The ONLY module that contains SQL (Kysely on `pg`); one file per domain; every function is `(ctx, input?) => Promise<…>`. Callers: `apps/web` routes/hooks (T2.4, T3.2, T4.3, T5.x, T6.x), `apps/worker` handlers (graph/library/llm/memory/runner/cleanup queues), and the T1.4 jobs wiring. They get plain camelCase row objects and typed errors; no HTTP codes, no Zod route schemas. FROM-SPEC (spec:92 "the only module with SQL; one file per domain; `ctx` first argument", spec:99 "ESLint bans `pg` and `kysely` imports outside `packages/shared/src/repositories`").

D1  Trust. `ctx.userId` is trusted (verified key or `local`). Everything else is untrusted: ids, cursors, labels, paths, free text, and any extra keys on an input object. Rules: (a) every value reaches SQL as a bound parameter, never concatenated; identifiers (table, column, order direction) come only from fixed lists in the code; (b) `userId` is read ONLY from `ctx`; an input carrying `userId`, `user_id` or `ownerId` is ignored (a create made with ctx B and `{userId:'user-a'}` stores user B); (c) `ctx.projectId` is trusted only together with `userId`: every project-scoped query filters `user_id = $user AND project_id = $project`, so a forged project id of another user matches nothing. Prevents: cross-user reads/writes, SQL injection, mass assignment. FROM-SPEC (spec:140 "`userId` comes from the verified key, never from a body").

D2  Limits (module constants in one exported object `limits`, read at call time, so a test can change them):
    `limits.maxPage = 500` (a list's `limit` is clamped to 1..maxPage, inclusive: 500 valid, 501 gives 500) FROM-SPEC (spec:146 "limit ≤ 500");
    `limits.defaultPage = 50` YOUR-CHOICE (spec gives no default for lists; 50 is the dashboard-sized page);
    `limits.statementTimeoutMs = 5000` default for `createDb` (the value applied to each connection as `statement_timeout`) FROM-SPEC (spec:161 "`store_timeout` 504 Postgres statement timeout (5 s on `/api`)"); workers pass their own value;
    `limits.manyIds = 20` (`memory.getMany` ids; 21 gives `RepoError('invalid')`) FROM-SPEC (spec:536 "`mem_get` `{ids[] ≤ 20}`");
    `limits.maxFailures = 3` is NOT here (T6.1 owns the retry rule; D7).

D3  Output and error format.
    Single read: the row, or `null` when it does not exist OR belongs to another user (the two cases are indistinguishable; the route turns both into `404 not_found`). FROM-SPEC (spec:155 "`not_found` … missing id, or another user's id").
    List: `{ rows: Row[], next: string | null }` for keyset lists (D4 for the cursor); a plain array for lists that are bounded by definition (e.g. `runner.listSteps`, `library.listVersions`).
    Write that targets one existing row: the updated row, or `null` when absent/foreign; bulk deletes and counters return the number of rows changed (`number`).
    Rows are camelCase objects; they include `userId` (equal to the ctx user) and exclude vector/`tsv` columns unless the function name says so (`…Vectors`, `nearest`). Timestamps are `Date`, bigint columns that fit 2^53 are `number`.
    Errors are instances of `RepoError` (has `code: string`, `message`, optional `detail`). Codes used by this module, taken from the spec's error table: `conflict` (ConflictError; version/label race, illegal state transition, unique-index violation on one-running-run), `not_found` (create under a project that is missing or not the user's), `invalid` (bad cursor, `latest` label, too many ids), `store_timeout` (StoreTimeoutError; Postgres `57014` query_canceled). Anything else from `pg` is rethrown unchanged (the route turns it into `500 internal` with only the class name). FROM-SPEC (spec:150-162 error table; spec:161 `store_timeout`; spec:155 `conflict` 409 "version or label race, illegal state transition"). Row/list shapes: YOUR-CHOICE.

D4  Bad input. A missing ctx (`undefined`, `null`, no `userId`, `userId` empty or only whitespace) throws a synchronous-looking `TypeError('ctx.userId required')` BEFORE any SQL (the promise rejects; no query is sent). A project-scoped function called without `ctx.projectId` rejects with `TypeError('ctx.projectId required')`. Bad cursors (not the base64url JSON this module issues: `{t: ISO time, id: string}`), more than `limits.manyIds` ids, and a `latest` label in `library.moveLabels` reject with `RepoError` code `invalid`. A limit below 1 or above `maxPage` is clamped, not an error (the route's Zod already rejects it). First problem wins (no error lists). Keyset order is `(created_at, id)` descending; the cursor is the last row's pair; pages never overlap or skip when rows share a timestamp. FROM-SPEC (spec:146 keyset on `(created_at, id)`, limit ≤ 500; spec:336 `latest` refused). Messages and cursor encoding: YOUR-CHOICE.

D5  Odd but harmless input stays valid: an empty list (`[]`, `{rows: [], next: null}`); a read or update of an id that does not exist → `null` / `0`, never a throw; updating with an empty patch → returns the current row; deleting something already deleted → `0`; extra unknown keys on an input object are ignored (D1b); `ctx.projectId` set on a function that does not need it is ignored; the same create twice with the same natural key returns the existing row where this list says "upsert" (D14). A ctx whose `userId` has no rows at all (new user) just sees empty results. judgment: tolerant by default (D8). YOUR-CHOICE.

D6  Must never:
    (a) run a query on a table that has `user_id` without `user_id = ctx.userId`, or on a table without that column without reaching it through its parent row that has it, in the SAME statement (join or sub-select); never "load the parent in one query, trust it in the next";
    (b) edit its argument objects (inputs may be deep-frozen);
    (c) leave a transaction open on a throw (use Kysely `transaction().execute`, which rolls back);
    (d) call anything that is not the database inside a transaction (no HTTP, no Redis, no timers);
    (e) hang: every connection has the `statement_timeout` of D2; a timeout becomes `StoreTimeoutError`;
    (f) delete rows except through the functions listed as deleting in D14 (memories and capabilities are soft-deleted; `cap_blobs` only through `system.cleanup.deleteUnreferencedBlobs`);
    (g) log row contents, ids of other users, prompts, memory text, file contents or the connection URL;
    (h) open more than `max` connections (default 5), or leave connections open after `db.close()`;
    (i) return another user's row through an error message (a `conflict` message never contains the other row's data).
    FROM-SPEC (spec:140 test `tenancy`; spec:134 "`decisions` and `events`… dropped": no such tables are touched) for (a); the rest YOUR-CHOICE.

D11 Tenancy mechanism. One predicate rule per table kind: tables with `user_id` filter `user_id = ctx.userId` (plus `project_id` where project-scoped, D1c); tables without it join to the parent that has it in the same statement: `capability_versions`, `cap_files`, `cap_vectors` via `capabilities`; `wf_steps` via `wf_runs`; `session_summaries` via `sessions`. A writer to a child table first proves ownership with the same join (`insert … select … where parent.user_id = $user`) and writes 0 rows (returns `null`/`0`) when the parent is not the user's. `cap_blobs` are per user (unique `(user_id, hash)`): a blob is read only through `cap_files` of the user's own versions or with `user_id = ctx.userId`. FROM-SPEC (spec:140, spec:399 `cap_blobs (user_id, hash)`). Join choices: YOUR-CHOICE.

D12 The gate test `tenancy` (file `tenancy.test.ts`, Vitest; this is what "`tenancy`" means):
    (1) builds a scratch schema `ctc_t13_<random>` in the scratch Postgres with the T1.2 migrations (never `ctc`, `ctc_eval`, `ctc_own`; it refuses a URL that is not `127.0.0.1:18304`), drops it in `afterAll`;
    (2) seeds users `user-a` and `user-b`, each with at least one row in EVERY table, using this module's own write functions;
    (3) enumerates every function of every domain object in `createRepositories(db)` (except `system`) by reflection and requires a case for each in `tenancy.cases.ts` (a function with no case FAILS the test, so a later task cannot add a function without a tenancy case; a case for a function that does not exist also FAILS);
    (4) per case, with ctx B and A's ids: a reader returns `null`/`[]`/`{rows: []}`/`0`; a writer returns `null`/`0` and A's row is byte-for-byte unchanged afterwards; a creator ignores a `userId` key of A in its input and stores B;
    (5) the cases also run with ctx B + `projectId` of A's project: same zero result;
    (6) a structural test reads `information_schema` and fails if any table in the schema, other than the migration stamp table, has neither a `user_id` column nor a foreign-key path to a table that has one;
    (7) calls every function with ctx `undefined` and with `{userId: ''}` and expects the `TypeError` of D4 and zero queries sent (counted through a Kysely log plugin);
    (8) asserts that the set of `system` functions equals the allowlist of D13 exactly.
    FROM-SPEC (spec:140 "user B's ctx reads zero of user A's rows on every repository function"; spec:757 gate name); the numbered parts: YOUR-CHOICE.

D13 System functions (the only cross-user ones). Spec says every function takes `ctx`; these need to see all users (auth runs before a ctx exists; workers serve every user), so they live in `repos.system`, take `SystemCtx` first (created only by `createSystemCtx(reason)`; reason is a non-empty string; the type is branded so a `Ctx` does not fit), and the allowlist is exactly:
    `system.apiKeys.findByHash(sctx, keyHash) → { id, userId } | null` (not revoked only);
    `system.jobs.listQueued(sctx, limit) → JobRow[]` (status `queued`, oldest first, `limit` clamped 1..500);
    `system.jobs.markRunning(sctx, id) → boolean` (true when the row went `queued|failed|running → running`, attempts + 1; false for `done|dead` or no row);
    `system.jobs.markDone(sctx, id, result?) → void`; `system.jobs.markFailed(sctx, id, error) → void` (status `failed`); `system.jobs.markDead(sctx, id, error) → void`; `system.jobs.markQueued(sctx, id) → void` (any status except `done` → `queued`, keeps `error`); `system.jobs.setProgress(sctx, id, progress) → void` (0..1 clamped);
    `system.runner.listRunningSteps(sctx) → StepRow[]` (restart sweep: status `running`, all users);
    `system.cleanup.listFinishedRuns(sctx, olderThanDays) → RunRow[]` (worktree cleanup candidates);
    `system.cleanup.deleteUnreferencedBlobs(sctx) → number` (blobs no `cap_files` row references);
    `system.cleanup.pruneIdempotencyKeys(sctx, olderThanDays = 30) → number`.
    Each ends with `where`-clauses that are still explicit (no `select *` without a reason). These JobRow-level functions are the T1.4 jobs wiring: T1.4 binds them as `(id) => repos.system.jobs.markRunning(sctx, id)`. FROM-SPEC for the need (spec:196 "the worker polls `jobs` every 5 s", spec:688 restart sweep, spec:687 cleanup, spec:427 blob cleanup, spec:131 "pruned after 30 days", spec:139 auth by hashed key); the allowlist itself and names: YOUR-CHOICE.
