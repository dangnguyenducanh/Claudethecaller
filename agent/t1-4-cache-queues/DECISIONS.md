D1  Trust. Redis contents are not trusted for correctness: an L2 value that is not valid JSON (or, for vectors, not a multiple of 4 bytes) is treated as a miss and its key is deleted. Queue payloads are re-validated with Zod when the worker consumes them (a stale or poisoned payload must not crash the worker). Key parts that come from callers (`userId`, `projectId`, epoch) must match `^[^:\s]{1,128}$` (no colon, no whitespace, not empty, at most 128 chars) so two different tuples can never build the same key (`a:b`+`c` vs `a`+`b:c`); the only free-form part is the last one (`cwd` in `proj:`), which may contain colons; a violation throws `TypeError('invalid key part: <name>')` synchronously (a programmer error, never a Redis error). Prompt and text values are hashed (`sha1`), never put in a key. Prevents: cache poisoning across users, key collisions. FROM-SPEC for the key shapes (spec:172-180); the validation rule: YOUR-CHOICE.

D10 Cache read/write semantics. `get`: L1 (a hit younger than its expiry returns, and is moved to most-recent) → else L2 (one `GET` + `PTTL` pipeline; a hit fills L1 with expiry = min(Redis TTL, `l1MaxAgeS`); a key with TTL 0 or -2 is not copied to L1) → else `undefined`. `set`: writes L1 first (expiry = min(ttl, `l1MaxAgeS`)), then L2 with `EX ttl`; the L1 write happens even when L2 fails. `del`: removes the keys from L1 and L2. Values are JSON (`JSON.stringify`/`parse`); vectors are stored as raw little-endian float32 bytes (4,096 bytes for 1,024 dims, a fifth of the JSON size) and read back as `Float32Array`. `L1` stays active while Redis is down (judgment: serving an in-process hit costs nothing and the entry cannot outlive `l1MaxAgeS`). FROM-SPEC for the order L1 → L2 → source and the 256 entries (spec:170); everything else (JSON/binary, `l1MaxAgeS`, fill rule): YOUR-CHOICE. Two readers differ on "cache skipped while Redis is down": here only L2 is skipped.

D11 Fail-open breaker. Every L2 call is bounded by `redisTimeoutMs` (ioredis `commandTimeout` plus an outer race). A call that exceeds it, or fails with a connection or socket error, marks Redis down for `downForMs`; while down no L2 call is attempted (`get` → miss, `set`/`del`/`hitRate`/epoch → skipped). When the window ends, the next call is the probe: success closes the breaker, failure re-opens it for another `downForMs`. A server reply that is an error (`ReplyError`, e.g. a bad argument) does NOT open the breaker. `cache.up` is `false` exactly while down. ioredis options: `enableOfflineQueue: false`, `maxRetriesPerRequest: 0`, `lazyConnect: true` with a capped reconnect strategy (`min(50 * attempt, 1000)` ms) so a restarted Redis is found again. FROM-SPEC (spec:170, spec:205 "Redis down | 20 ms timeout | cache and rate limit skipped"); the probe rule and options: YOUR-CHOICE.

D12 Epochs. `epoch.get(kind, user, project)` returns the token: an in-process memo younger than `epochMemoMs` first; else Redis `GET epoch:<kind>:<user>:<project>`; if the key does not exist, `SET … NX EX epochTtlS` a fresh token and use whichever value Redis holds; the memo is updated. If Redis is down or fails: the memo if it is younger than `epochStaleS`, else `null` (meaning "unknown: do not cache by epoch"). `epoch.rotate(kind, user, project)` sets a new random token (`SET … EX epochTtlS`), updates the memo, publishes `{v:1, event:'epoch', kind, userId, projectId, epoch}` on `ctc:inval`, and returns the token (`null` if Redis is down: nothing was rotated). A token is random, not a counter, so a Redis restart cannot resurrect old cache keys. Memos are also updated from received `epoch` messages (D13). FROM-SPEC (spec:182 "`graph_epoch` and `mem_epoch` are per-project tokens in Redis. Every graph rebuild or memory write rotates them, so old keys die without a scan"); memo/stale/NX/message details: YOUR-CHOICE. Open: the spec also mentions a Postgres `graph_epoch` (spec:205); this module has Redis only (OPEN file).

D13 `ctc:inval`. `publishInval(msg)` validates `msg` (Zod, same shape as D3), publishes JSON, never throws (Redis down → skipped). `subscribeInval(cb)` opens its OWN Redis connection (never the command connection), subscribes to the channel, and returns a handle whose `close()` unsubscribes and disconnects. Per received message: parse + Zod-validate (invalid or unknown event → ignored); an `epoch` event updates the epoch memo; every event except `epoch` clears the whole L1 (judgment: L1 holds at most 256 entries and refills in one request each; precise invalidation is not worth the code); then `await cb(msg)` inside a try/catch (an error in `cb` is logged with the error class and the next message is still delivered). Whenever the connection is (re)established, clear L1 (messages may have been missed); `cb` is NOT called on reconnect, the web's 60 s Postgres poll covers missed RAM reloads (spec:205). After `close()` no callback runs. FROM-SPEC (spec:182, spec:205); clear-everything rule, own connection and validation: YOUR-CHOICE.

D14 Rate limit counter. `hitRate(userId)` does one atomic call (`EVAL`, or `MULTI` with `INCR` + `EXPIRE <rateWindowS> NX`) on `rl:<user>:<minute>` and returns the new count (this request included): a FIXED window per calendar minute, as the spec says. Redis down or failing → returns `0` (the limit is skipped). The caller compares with `cacheLimits.rateLimitPerMin` (600; over it → `429`/empty hook reply, apps/web). FROM-SPEC (spec:141 "600 requests/min per key (Redis fixed window)", spec:179 `rl:{user}:{minute}` 60 s, spec:205). Note: CLAUDE.md memory says the Python daemon moved to a sliding window; the 007 spec says fixed; this follows the 007 spec (OPEN file).

D17 `submitJob`. In this order: (1) parse the payload (D4); (2) `id = input.id ?? randomUUID()`; (3) `await create({id, queue, kind, payload})`, the row is the truth and is written before BullMQ (a throw from `create` propagates: nothing was enqueued); (4) `queue.add(kind, { id, payload }, { jobId: bullJobId(id) })` bounded by `queueLimits.submitTimeoutMs` (1000 ms); success → `enqueued: true`; any failure or timeout → swallowed, logged, `enqueued: false` (the row stays `queued`; the poller of D20 picks it up). D18 Consuming one attempt (`runAttempt`; the BullMQ processor calls it with `data = {id, payload}`):
    (1) parse `data.payload` with the schema of `(queue, kind)`; invalid → `port.markDead(id, 'payload_invalid')` and throw `UnrecoverableError('payload_invalid')`;
    (2) `claimed = await port.markRunning(id)`; `false` (row is `done`, `dead` or missing) → return `{ skipped: true }` without running the handler; a throw from the port propagates (BullMQ retries; the handler did not run);
    (3) run the handler with the timeout of D19 and `ctx.setProgress`;
    (4) success → `port.markDone(id, result)` (retried up to `retryWriteTries` times, 100 ms apart; if it still fails log and return, the job is complete and a stale `running` row is accepted: judgment) and return `{ skipped: false, result }`;
    (5) failure → `final = err instanceof UnrecoverableError || attemptsMade + 1 >= maxAttempts`; `final` → `port.markDead(id, text)`, else `port.markFailed(id, text)`; `text` = `<ErrorClass>: <message>` cut to 1,000 chars, except a `JobDropped` whose text is `dropped:<code>`; then rethrow so BullMQ applies backoff or moves the job to failed. A missing handler is the same path as any failure (error `no_handler`). The `dlq-retry` queue has no `jobs` row: its processor calls the dlq handler directly, without `runAttempt`.
    States written: `queued → running → done`; `running → failed` (attempts left) `→ running`; `running → dead` (exhausted, unrecoverable, or dropped). FROM-SPEC (spec:196 "A job that fails every attempt becomes `jobs.status = dead`", spec:130 status values, spec:190 "retry once, then `jobs.error`"); `JobDropped`, `payload_invalid`, claim rule and write retries: YOUR-CHOICE.

D20 Poller (`pollOnce`; `startWorkers` calls it every `pollEveryMs` unless `poll: false`, never two at once). One tick: `isRedisUp()` (default: a Redis `PING` answered within 500 ms). Redis UP: `port.listQueued(200)`; for each row whose `updatedAt` is older than `staleAfterMs` (so a row just created is not raced with its own BullMQ add) and whose `queue` is not `dlq-retry`: `queue.add(kind, {id, payload}, {jobId: bullJobId(id)})` (BullMQ ignores an id it already has) → result `reenqueued`. Redis DOWN: one tick runs each row that one `listQueued(200)` call returns, once, oldest first and serially (a row that fails and goes back to `queued` waits for the next tick; the single llama slot and one worker make parallelism pointless; ponytail: serial, per-queue concurrency is not used in this mode) and run each directly through `runAttempt` with `attemptsMade = row.attempts` (the claim increments `attempts`) and `maxAttempts = QUEUES[queue].attempts`: success → done; failure with attempts left → the row goes back to `queued` via `port.markQueued` and waits for the next tick (fixed delay of one tick instead of the exponential backoff: ponytail); no attempts left → `dead` → result `ran`.
